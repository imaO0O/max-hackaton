# Версии, обновление сервера и откат

Цель — при любой ошибке за минуту вернуть рабочую версию.

## Как устроено

- **Теги.** Каждая проверенная версия отмечается тегом `vX.Y.Z` в git, список — в [CHANGELOG.md](../CHANGELOG.md).
- **Образы.** `scripts/deploy.sh` собирает образ каждой версии под своим тегом `posle9:<коммит>` и хранит 6 последних. Откат к сохранённому образу — без пересборки, за секунды.
- **Автооткат.** После обновления скрипт ждёт `/api/health` до 90 секунд. Если сервис не ответил `ok` с работающим ботом, скрипт сам возвращает версию, которая работала до обновления.
- **Копия базы.** Перед каждым обновлением — копия базы в `backups/`.
- **Рабочая папка всегда на `main`.** Нужная версия собирается в отдельной временной копии (`git worktree`), поэтому скрипты и `compose.yaml` не пропадают при откате на старую версию.
- **История** развёртываний — в `.deploy/history`.

## Команды на сервере

```bash
./scripts/deploy.sh                    # обновить до последнего main
./scripts/deploy.sh v0.2.0             # развернуть версию по тегу, ветке или коммиту
./scripts/deploy.sh --rollback         # вернуть предыдущую рабочую версию
./scripts/deploy.sh --rollback v0.1.0  # вернуть конкретную версию
./scripts/deploy.sh --status           # что работает сейчас, сохранённые образы, история
```

При первом запуске скрипт сохраняет образ, который работает сейчас, как `posle9:before-<дата>` — к нему тоже можно вернуться: `./scripts/deploy.sh --rollback before-<дата>`.

## Выпуск версии

1. PR слит в `main`, проверка в GitHub Actions зелёная.
2. На сервере: `./scripts/deploy.sh`.
3. Проверка в MAX по `docs/max-check.md`.
4. Если всё работает — тег и запись в `CHANGELOG.md`:

```bash
git tag -a v0.3.0 -m "Кратко, что вошло"
```

```bash
git push origin v0.3.0
```

Если что-то сломалось — `./scripts/deploy.sh --rollback`, затем исправление отдельным PR.

## Откат и данные

База переживает откат: схема меняется только **добавляющими** миграциями (новые таблицы и столбцы), поэтому старая версия кода работает с базой новой версии — лишние таблицы она просто не использует. Это правило действует до конца периода проверки: миграции, которые удаляют или переименовывают таблицы и столбцы, не делаем.

Если после ошибки нужно вернуть и данные, есть копия перед каждым обновлением — восстановление описано в README, раздел «Резервная копия базы».

## После сдачи

Сдаётся зафиксированный коммит. После 30.09 12:00 на сервере работает ровно он: `./scripts/deploy.sh <тег сданной версии>`, дальше сервер не обновляем. Откат допустим только на эту же версию, например после сбоя сервера.
